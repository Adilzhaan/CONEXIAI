# Промт для Claude Code — Оценка риска по формулам клиента (по каждому типу отдельно)

> Вставь в Claude Code как задачу. Бэкенд — **FastAPI**. Сначала прочитай существующий код оценки рисков, не дублируй.

---

## Что меняем (главное)

**Сейчас:** ИИ оценивает риск «на глаз» — выдаёт балл по своему усмотрению. Непрозрачно и неуправляемо.

**Нужно:**
1. Считать риск по **конкретным формулам**, детерминированно. ИИ больше НЕ ставит итоговый балл.
2. **Каждый тип кризиса оценивается отдельно**, своей формулой. НЕ сводить в общий риск-скор.
3. У клиента может быть **своя формула — она встраивается вместо стандартной**, на каждый тип отдельно.
4. Уведомление конкретное: не «у вас кризис», а **«репутационный кризис»** — с типом, источником, факторами.

**Новая роль ИИ:** читает сигнал и **вытаскивает из текста числа-факторы** (0–10) с обоснованием. Балл по каждому типу считает **формула**, не ИИ.

```
Сигнал → [ИИ извлекает факторы 0–10] → [формула типа считает балл] → [тревога по этому типу]
```

---

## Принцип №1: каждый тип риска — НЕЗАВИСИМО

**Критично:** НЕ смешивать типы в одну цифру. Репутационный и операционный риск разной природы — усреднять их некорректно. Каждый тип:
- считается своей формулой,
- имеет свой балл 0–100,
- имеет свой порог тревоги,
- даёт своё уведомление.

```
financial     → financial_score      (0–100)
operational   → operational_score    (0–100)
reputational  → reputational_score   (0–100)
regulatory    → regulatory_score     (0–100)
supplier      → supplier_score       (0–100)
```

Никакого `total_risk` для принятия решений. (Опц. на обзорном дашборде можно показать список типов с баллами — но это витрина, а не единая оценка.)

Шкала уровней (к каждому типу): `0–20` низкий · `21–50` средний · `51–75` высокий · `76–100` критический.

---

## Стандартные формулы (дефолт)

Каждый фактор ИИ выдаёт в шкале **0–10**. Результат нормируется к 0–100.

```python
financial    = clamp(probability * loss, 0, 100)                          # 2 фактора (max 100)
operational  = clamp(probability * impact * duration / 10, 0, 100)        # 3 фактора (/10)
reputational = clamp(reach * sentiment * audience_influence / 10, 0, 100)
regulatory   = clamp(inspection_probability * potential_fine, 0, 100)
supplier     = clamp(failure_probability * downtime_loss, 0, 100)
```

Нормировка: 2 фактора дают 0–100 сразу (10×10); 3 фактора — делим на 10 (10×10×10 → /10 = 100).

---

## Принцип №2: формулы клиента ВМЕСТО стандартных (на каждый тип)

Если у клиента своя методология — его формула заменяет стандартную **для конкретного типа**, остальные остаются. Делается на уровне настройки/админа, один раз, с валидацией — НЕ casual-правка рядовым юзером.

### Формулы как данные (не хардкод)

```python
formula_defs(
  id, company_id, domain,        # тип риска: financial | operational | ...
  source[standard|custom],
  expression text,               # напр. "reach * sentiment * audience_influence / 10"
  variables jsonb,               # какие факторы извлекает ИИ для этой формулы
  is_active bool, version, created_by, created_at
)
```

- Стандартная формула на каждый тип активна по умолчанию.
- Клиент даёт свою на тип → создаём `custom` → после валидации делаем активной для этого типа.
- ИИ-экстрактор читает `variables` активной формулы типа и извлекает именно нужные факторы.

### Безопасный расчёт (НЕ eval)

Выражения считаются через **sandbox-эвалюатор** (`asteval` с whitelist), НЕ `eval()`/`exec()`:
- разрешены только переменные из `variables` и функции `min, max, clamp, abs, log, sqrt, pow`;
- любой другой узел AST → reject при валидации;
- результат принудительно `clamp(0, 100)`.

### Валидация перед активацией (обязательна)

```
1. Parse      — выражение в AST
2. Whitelist  — только разрешённые переменные/функции, иначе reject
3. Range      — прогон на тестовых входах, результат в 0–100
4. Backtest   — пересчёт на исторических сигналах: показать клиенту,
                как его формула сработала бы на прошлых кейсах
5. Activate   — только после 1–4, новой версией (старая откатываема)
```

### Эндпоинты (admin-уровень)

```
GET  /formulas?domain=            — формулы типа (standard + custom)
POST /formulas                    — создать кастомную формулу типа
POST /formulas/{id}/validate      — parse + whitelist + range + backtest
POST /formulas/{id}/activate      — сделать активной для типа (после валидации)
POST /formulas/{id}/rollback      — вернуть предыдущую активную
```

### Фолбэк

Если активная формула на проде дала ошибку/NaN → авто-откат на стандартную для этого типа + алерт админу. Расчёт не падает.

## ИИ-извлечение факторов (замена «оценки на глаз»)

Промпт к Claude возвращает строго JSON — числа 0–10 + обоснование. Никакого итогового балла от ИИ.

```
Ты — экстрактор факторов риска. НЕ оценивай общий риск и НЕ ставь итоговый балл.
Прочитай сигнал и оцени каждый фактор по шкале 0–10 (0=нет, 10=максимум).
Верни JSON. Для каждого типа дай короткое обоснование (1 строка).

{
  "financial":    {"probability": 0-10, "loss": 0-10, "why": "..."},
  "operational":  {"probability": 0-10, "impact": 0-10, "duration": 0-10, "why": "..."},
  "reputational": {"reach": 0-10, "sentiment": 0-10, "audience_influence": 0-10, "why": "..."},
  "regulatory":   {"inspection_probability": 0-10, "potential_fine": 0-10, "why": "..."},
  "supplier":     {"failure_probability": 0-10, "downtime_loss": 0-10, "why": "..."}
}
Если тип нерелевантен сигналу — ставь 0.
```

Бэк парсит JSON, клампит каждое значение 0–10, передаёт в активную формулу типа. **Балл считает код.** Обоснования сохраняем — для прозрачности.

## Настройка под юзера — ПО КАЖДОМУ ТИПУ (просто, без формул)

Юзер не трогает формулы. Настраивает каждый тип отдельно: следить/нет и когда поднимать тревогу.

### Модель конфига

```python
risk_configs(
  id, company_id, scope[user|department|company], owner_id,
  per_type jsonb,   # {
                    #   "financial":    {"enabled": true,  "threshold": 70},
                    #   "operational":  {"enabled": true,  "threshold": 60},
                    #   "reputational": {"enabled": true,  "threshold": 70},
                    #   "regulatory":   {"enabled": true,  "threshold": 80},
                    #   "supplier":     {"enabled": false, "threshold": 70}
                    # }
  preset str, version, updated_by, updated_at
)
```

`threshold` ∈ {60,70,80}, `enabled` bool — валидируется/клампится на бэке. Resolution: user → department → company.

### UI-контролы (человеческим языком)

```
Тип риска          Следить   Когда поднимать тревогу
───────────────────────────────────────────────────
Репутационный       [вкл]    ○ Рано  ● Средне  ○ Поздно
Операционный        [вкл]    ● Рано  ○ Средне  ○ Поздно
Финансовый          [вкл]    ○ Рано  ○ Средне  ● Поздно
Регуляторный        [вкл]    ○ Рано  ○ Средне  ● Поздно
Поставщиков         [выкл]   —
```
- Тумблер «Следить» = вкл/выкл тип.
- «Рано/Средне/Поздно» = порог 60/70/80 для этого типа (число скрыто).

### Живой превью (по типам, debounce 300мс)

```
На ваших данных (последние 120 сигналов):
  Репутационный:  в тревоге было 2 → станет 3
  Операционный:   в тревоге было 1 → станет 2
  (пример: «вирусный негатив в Instagram» — репутационный 68)
```

**Кнопки:** `[Сохранить]` `[Сбросить к стандарту]`

## Уведомления — конкретные (НЕ «у вас кризис»)

Раз каждый тип отдельно, уведомление называет **что именно** и **откуда**:

```
🔴 Репутационный кризис
   Score: 68 (высокий)  ·  порог 70 превышен динамикой за 24ч
   Источник: Instagram (50k охват), 3 СМИ
   Факторы: Охват 8 · Тональность 9 (резкий негатив) · Влияние аудитории 9.4
   Почему: вирусный негативный пост, подхвачен медиа
   → Открыть карточку / Запустить сценарий
```

Каждое уведомление содержит: **тип кризиса** (в заголовке), **балл + уровень + какой порог сработал**, **источник(и)**, **факторы формулы + обоснование ИИ**, **действие**. Горит репутационный, операционный спокоен → уходит только репутационный алерт.

---

## Прозрачность (важно для доверия)

В карточке риска видно, как получилась цифра:

```
Репутационный риск: 68 (высокий)
  Формула: Охват 8 × Тональность 9 × Влияние аудитории 9.4 / 10 = 68
  Источник: Instagram (50k), 3 СМИ
  Почему (ИИ): «вирусный негатив в Instagram, 50k охват, резко негативный тон»
```

Юзер видит тип, формулу, факторы, источник и почему ИИ так оценил. Никакой магии.

---

## Безопасность (невидима юзеру)

- `threshold` ∈ {60,70,80}, `enabled` bool — валидируется на бэке.
- Простые изменения (следить/порог) — сразу, без апрувов.
- Кастомная формула — только через валидацию + бэктест + активация (admin).
- Версионирование; в записи риска — `formula_version`, `config_version` и извлечённые факторы.
- История **не пересчитывается** задним числом.

```

POST /risk/score              — факторы + config → балл ПО КАЖДОМУ типу + уровень + флаг тревоги
```

## Acceptance Criteria

1. 5 стандартных формул реализованы как чистые функции + юнит-тесты (включая нормировку 3-факторных). Формулы хранятся как данные, не хардкод.
2. ИИ возвращает только факторы 0–10 + обоснования; **итоговый балл считает код** (тест: при одинаковых факторах балл детерминирован).
3. Каждый тип оценивается **независимо**; **нет** общего `total_risk`. Тревога — по каждому типу против его порога (тест: высокий репутационный + низкий операционный → тревога только по репутационному).
4. Кастомная формула заменяет стандартную **для конкретного типа**; активируется только после валидации (parse+whitelist+range+backtest); тест на reject небезопасного выражения; авто-фолбэк при ошибке.
5. Настройка по типу: `enabled` вкл/выкл, `threshold`∈{60,70,80}; выключенный тип не мониторится и не шлёт тревог (тест).
6. `/preview` показывает «было→стало» **по типам** на реальных сигналах и **ничего не пишет** в БД.
7. Уведомление содержит тип, балл, сработавший порог, источник, факторы + обоснование ИИ.
8. Карточка риска показывает тип, формулу, факторы, источник, обоснование.
9. История не пересчитывается при смене конфига/формул. Alembic-миграции чистые.

## Чего НЕ делать

- НЕ давать ИИ ставить итоговый балл — только извлекать факторы.
- НЕ сводить типы в общий риск-скор для принятия решений.
- НЕ хардкодить формулы — хранить как данные (`formula_defs`).
- НЕ использовать `eval()`/`exec()` для кастомных формул — только sandbox + whitelist.
- НЕ активировать кастомную формулу без валидации + бэктеста.
- Рядовому юзеру НЕ давать править формулы на ходу — только следить/порог по типам.
- НЕ слать общее «у вас кризис» — всегда конкретный тип + источник.
- НЕ пересчитывать историю при смене конфига/формул.

## Порядок реализации

1. 5 стандартных формул как чистые функции + юнит-тесты.
2. Формулы как данные: `formula_defs` + стандартный набор на каждый тип.
3. ИИ-экстрактор (`/risk/extract`, читает variables активной формулы) + парсинг/clamp.
4. `/risk/score` — балл по каждому типу + флаг тревоги (без агрегата).
5. Кастомные формулы: safe-эвалюатор + валидация + бэктест + activate/rollback + фолбэк.
6. Конфиг `risk_configs` (per_type) + resolver + миграции.
7. Эндпоинты config/preview/reset.
8. Уведомления по типу (тип + источник + факторы).
9. UI: настройка по типам → превью по типам → прозрачная карточка риска.
