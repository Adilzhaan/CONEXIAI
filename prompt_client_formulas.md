# Промт для Claude Code — Оценка риска по формулам клиента + настройка под юзера

> Вставь в Claude Code как задачу. Бэкенд — **FastAPI**. Сначала прочитай существующий код оценки рисков.

---

## Проблема (что меняем)

**Сейчас:** ИИ оценивает риск «на глаз» — выдаёт score по своему усмотрению. Это непрозрачно и неуправляемо.

**Нужно:** считать риск по **конкретным формулам клиента**, детерминированно. ИИ больше НЕ ставит оценку сам.

**Новая роль ИИ:** читает сигнал (новость, пост, ответ руководителя) и **вытаскивает из текста числа-факторы** (каждый по шкале 0–10) с коротким обоснованием. Дальше **оценку считает формула**, не ИИ. + юзер может подстраивать.

```
Сигнал → [ИИ извлекает факторы 0–10] → [формула клиента считает score] → [юзер тюнит]
```

---

## ФОРМУЛЫ КЛИЕНТА (реализовать ровно эти)

Каждый фактор ИИ выдаёт в шкале **0–10**. Нормируем результат к 0–100.

```python
# Финансовый риск
financial    = clamp(probability * loss, 0, 100)                       # 2 фактора: 10*10=100

# Операционный риск
operational  = clamp(probability * impact * duration / 10, 0, 100)     # 3 фактора: /10 → 0..100

# Репутационный риск
reputational = clamp(reach * sentiment * audience_influence / 10, 0, 100)

# Регуляторный риск
regulatory   = clamp(inspection_probability * potential_fine, 0, 100)

# Риск поставщика
supplier     = clamp(failure_probability * downtime_loss, 0, 100)
```

Нормировка: формулы с 2 факторами дают 0–100 сразу (max 10×10); с 3 факторами — делим на 10 (max 10×10×10=1000 → /10 = 100).

### Общий риск-индекс компании

```python
total_risk = sum(domain_score[d] * domain_weight[d] for d in DOMAINS) \
             / sum(domain_weight[d] for d in DOMAINS)
```

`domain_weight` — настраивается юзером (см. ниже). Дефолт 1.0 у всех.

### Шкала уровней

`0–20` низкий · `21–50` средний · `51–75` высокий · `76–100` критический

## ИИ-извлечение факторов (замена «оценки на глаз»)

Промпт к Claude должен возвращать строго JSON — числа 0–10 + обоснование. Никакого «итогового score» от ИИ.

```
Ты — экстрактор факторов риска. НЕ оценивай общий риск.
Прочитай сигнал и оцени каждый фактор по шкале 0–10 (0=нет, 10=максимум).
Верни JSON. Для каждого фактора дай короткое обоснование (1 строка).

Факторы по типам риска:
- Финансовый: probability, loss
- Операционный: probability, impact, duration
- Репутационный: reach, sentiment, audience_influence
- Регуляторный: inspection_probability, potential_fine
- Поставщик: failure_probability, downtime_loss

Формат:
{
  "financial":    {"probability": 0-10, "loss": 0-10, "why": "..."},
  "operational":  {"probability": 0-10, "impact": 0-10, "duration": 0-10, "why": "..."},
  "reputational": {"reach": 0-10, "sentiment": 0-10, "audience_influence": 0-10, "why": "..."},
  "regulatory":   {"inspection_probability": 0-10, "potential_fine": 0-10, "why": "..."},
  "supplier":     {"failure_probability": 0-10, "downtime_loss": 0-10, "why": "..."}
}
Если тип риска нерелевантен сигналу — ставь 0.
```

Бэк парсит JSON, клампит каждое значение в 0–10, передаёт в формулы. **Score считает код, не ИИ.** Обоснования сохраняем — для прозрачности «почему такая оценка».

## Настройка под юзера (просто, без формул)

Юзер не трогает формулы. Он крутит **важность каждого типа риска** и пороги. Это меняет `domain_weight` и тревоги — но не ломает расчёт.

### Модель конфига

```python
risk_configs(
  id, company_id, scope[user|department|company], owner_id,
  domain_weights jsonb,   # {financial, operational, reputational, regulatory, supplier} каждый 0–2
  trigger_threshold int,  # 60 | 70 | 80
  preset str,             # "balanced" | "custom" | ...
  version, updated_by, updated_at
)
```

`domain_weight` ∈ 0–2: `0` = игнорировать этот тип риска, `1` = обычно, `2` = очень важен. Клампится на бэке.

### UI-контролы (человеческим языком)

**Слайдеры важности типов риска:**
```
Насколько для вас важен каждый риск?

Финансовый       [——————●——]  важен
Операционный     [————●————]  средне
Репутационный    [————————●]  критичен
Регуляторный     [———●—————]
Поставщиков      [●————————]  не важен (выкл)
```
Левый край = «не важен / выкл» (weight 0), правый = «критичен» (weight 2).

**Порог тревоги:**
```
Когда поднимать тревогу?   ○ Рано(60)   ● Средне(70)   ○ Поздно(80)
```

**Живой превью** (обновляется при движении слайдера, debounce 300мс):
```
На ваших данных (последние 120 сигналов):
  Общий риск-индекс:  54 → 61
  В тревоге сейчас:   3 → 5 рисков
  Топ-тип:  Репутационный (68)
```

**Кнопки:** `[Сохранить]` `[Сбросить к стандарту]`

### Эндпоинты

```
POST /risk/extract        — вход: текст сигнала; выход: факторы 0–10 (ИИ) + обоснования
POST /risk/score          — вход: факторы + config; выход: domain_scores + total_risk + уровень
GET  /config              — текущий конфиг (+ позиции слайдеров)
PUT  /config              — сохранить (clamp 0–2, версия++)
POST /config/reset        — сброс к дефолту компании
POST /preview             — вход: черновик domain_weights/threshold; выход: было→стало (НЕ пишет в БД)
```

### Контракт /preview

```jsonc
// REQUEST
{ "domain_weights": {"reputational": 1.5, ...}, "trigger_threshold": 65 }
// RESPONSE
{
  "sample_size": 120,
  "total_before": 54, "total_after": 61,
  "alerts_before": 3, "alerts_after": 5,
  "top_domain": "reputational",
  "examples": [{"signal": "негатив в СМИ", "before": 44, "after": 52}]
}
```

## Прозрачность (важно для доверия)

В карточке риска показывать, **как получилась цифра**:
```
Репутационный риск: 68 (высокий)
  Охват 8 × Тональность 9 × Влияние аудитории 9.4 / 10 = 68
  Почему: «вирусный негатив в Instagram, 50k охват, резко негативный тон»  ← обоснование ИИ
```
Юзер видит и формулу, и факторы, и почему ИИ так оценил. Никакой «магии».

---

## Безопасность (невидима юзеру)

- `domain_weight` клампится 0–2, порог ∈ {60,70,80} — на бэке. Сломать нельзя.
- Простые изменения — сразу, без апрувов.
- Версионирование; в записи риска — `config_version` и извлечённые факторы.
- История **не пересчитывается** задним числом.
- Формула в коде **неизменна** — юзер меняет только важность и пороги.

## Acceptance Criteria

1. Реализованы ровно 5 формул клиента; есть юнит-тесты на каждую (включая нормировку 3-факторных).
2. ИИ возвращает только факторы 0–10 + обоснования; **итоговый score считает код** (тест: при одинаковых факторах score детерминирован).
3. `total_risk` = взвешенное среднее доменов; при `domain_weight=0` тип риска исключён из индекса.
4. Слайдер важности меняет вес только в 0–2; мусор на входе клампится (тест).
5. `/preview` показывает «было→стало» на реальных сигналах и **ничего не пишет** в БД.
6. Карточка риска показывает формулу + факторы + обоснование ИИ.
7. «Сбросить к стандарту» возвращает дефолт; история не пересчитывается.
8. Alembic-миграции чистые.

## Чего НЕ делать

- НЕ давать ИИ ставить итоговый score — только извлекать факторы.
- НЕ давать юзеру редактировать сами формулы — только важность типов и пороги.
- НЕ хардкодить границы в разных местах — одна точка истины.
- НЕ пересчитывать историю при смене конфига.

## Порядок реализации

1. 5 формул клиента как чистые функции + юнит-тесты.
2. ИИ-экстрактор факторов (`/risk/extract`) + парсинг/clamp.
3. `/risk/score` (формулы + domain_weights) + total_risk.
4. Конфиг `risk_configs` + resolver + миграции.
5. Эндпоинты config/preview/reset.
6. UI: слайдеры важности → порог → панель превью → прозрачная карточка риска.
