# Conexi — Задачи для разработки (Claude Code)

> Бэкенд: **FastAPI** (Python). LLM: **Claude API**. Источники: NewsAPI + RSS + соцсети/OSINT.
> Документ описывает, **что нужно собрать** — от фиксов до недостающего «правого края» (кризис-исполнение).
> Формат: эпики → задачи. У каждой задачи есть ID, что делать, эндпоинты/модули и acceptance criteria (AC).

## Как пользоваться этим файлом

1. Дай Claude Code этот файл и текущую кодовую базу.
2. Идти по эпикам сверху вниз: `EPIC 0` (баги) → `EPIC 1–2` (фундамент данных) → дальше.
3. Каждая задача — отдельный коммит/PR. AC = критерии готовности (Definition of Done).
4. Перед каждым эпиком Claude Code должен прочитать существующие модели и роутеры, чтобы не дублировать.

---

## Что уже есть (не трогаем без причины)

- Сбор сигналов из внешних/внутренних источников (Data Collection Layer)
- Signal Processing (фильтрация, кластеризация тем, определение источника)
- AI Risk Analysis + Risk Score `(Severity × Probability × Velocity) + Signal Density`, шкала 0–100
- Crisis Intelligence Dashboard (риск-индекс, топ-угрозы, динамика)
- Страницы индикаторов: Media, Social, Market, CI, HR, GR, PR
- Авторизация + ролевой доступ
- Пошаговый анализ, off-review интерфейс

# EPIC 0 — Фиксы багов (P0, срочно)

### TASK-0.1 — Индикаторы исчезают при переходе между шагами анализа
**Что:** состояние индикаторов теряется при навигации между шагами.
**Где:** state-менеджмент шага анализа + соответствующие GET-эндпоинты (проверить, что данные не пересоздаются на каждом шаге, а читаются из сохранённого `analysis_session`).
**AC:**
- При переходе вперёд/назад значения индикаторов сохраняются.
- Есть бэкенд-хранилище состояния сессии анализа (таблица `analysis_sessions`), фронт читает из него.
- Покрыто тестом: пройти 3 шага и вернуться — данные на месте.

### TASK-0.2 — Пробел в пароле ломает вход
**Что:** ведущие/хвостовые пробелы в пароле вызывают ошибку входа.
**Где:** эндпоинт аутентификации (валидация/нормализация ввода).
**AC:**
- Пароль НЕ триммится молча, если это меняет смысл — но ошибка должна быть понятной, а не 500.
- Корректная обработка: пробелы внутри пароля допустимы; ошибка входа отдаёт 401 с понятным сообщением, не падает.
- Тест на пароль с пробелами в начале/конце/середине.

### TASK-0.3 — Нет кнопки «Назад» в off-review интерфейсе
**Что:** в офф-ревью невозможно вернуться на предыдущий экран.
**Где:** роутинг off-review (если навигация серверная) + поддержка возврата состояния.
**AC:**
- Кнопка «Назад» возвращает на предыдущий шаг с сохранением введённых данных.
- Работает на всех экранах off-review.

# EPIC 1 — Разделение «Риск» vs «Инцидент» (P1, фундамент)

> Сейчас система их смешивает. Это базовая модель для всего «правого края».

### TASK-1.1 — Модель данных Risk / Incident / Crisis
**Что:** ввести три сущности и связи.
**Таблицы (Postgres):**
- `risks` — потенциальная угроза: `id, company_id, domain (PR/HR/GR/OR/MR/IM/CI), category, subtype, severity, probability, velocity, signal_density, risk_score, status, created_at`
- `incidents` — свершившийся факт: `id, company_id, risk_id (nullable), type, description, occurred_at, source, severity, status`
- `crises` — инцидент/риск, прошедший триггер: `id, company_id, incident_id, scenario_id, level (L1–L4), risk_score, opened_at, contained_at, stabilized_at, status`
**AC:**
- Миграции применяются чисто.
- Pydantic-схемы + CRUD-роутеры для каждой сущности.
- Risk Score считается только для `risks`; `incidents` — это факт без вероятности.

### TASK-1.2 — Классификатор «риск или инцидент»
**Что:** при поступлении сигнала AI определяет — это риск (вероятность) или уже инцидент (факт).
**Где:** сервис анализа сигналов + промпт к Claude.
**AC:**
- Эндпоинт `POST /signals/classify` возвращает `{kind: "risk"|"incident", domain, category, subtype, confidence}`.
- В UI индикаторов риск и инцидент визуально разделены.

# EPIC 2 — Crisis Taxonomy + сценарии риска с расчётом потерь (P1)

### TASK-2.1 — Справочник таксономии (3 уровня)
**Что:** загрузить классификацию из методички.
**Таблица:** `crisis_taxonomy (id, domain L1, category L2, subtype L3)`.
**Данные:** Domain = PR, HR, GR, OR, MR, IM, CI; категории и подтипы из документа (Media scandal, Salary crisis, Regulatory violation, Production failure, и т.д.).
**AC:**
- Сид-скрипт заполняет таблицу.
- `GET /taxonomy` отдаёт дерево.

### TASK-2.2 — Библиотека сценариев (Mining M-01…M-12 и др.)
**Что:** каталог отраслевых сценариев с триггерами и шагами.
**Таблица:** `scenarios (id, industry, code [M-01], title, level, license_impact, triggers jsonb, steps jsonb, hitl jsonb)`.
**AC:**
- Сид: минимум Mining M-01…M-12 из документа.
- `GET /scenarios?industry=mining` + `GET /scenarios/{code}`.

### TASK-2.3 — Формулы расчёта ущерба
**Что:** реализовать как чистые функции + эндпоинт.
**Формулы (из документа, валюта ₸):**
- `Total_Loss = Op_Loss + Reg_Loss + Rep_Loss + Stakeholder_Loss + Market_Loss`
- `Op_Loss = (P_per_hour × T_downtime) + (Demurrage × Metal_price)`
- `Reg_Loss = Fine_ADM + Fine_Env + License_Suspension_Penalty` (МРП 2026 = 3690 ₸)
- `Rep_Loss = Media_Impressions × CPM_KZ × Sentiment_Factor` (CPM 500–1500 ₸; негатив 1.5)
- `Market_Loss = (ΔMarketCap_% × EV) + ΔCost_of_Debt`
- `Stakeholder_Loss = Supplier_Fines + Employee_Churn_Cost + Community_Compensation`
**Где:** модуль `services/damage.py` + `POST /damage/estimate`.
**AC:**
- Каждая формула — отдельная функция с юнит-тестами на примерах из документа (напр. постмортем ≈ 65 млн ₸).
- Конфигурируемые коэффициенты (МРП, CPM, sentiment) в settings, не хардкод.

### TASK-2.4 — Развёрнутый сценарий риска для дашборда
**Что:** по риску AI генерирует «что произойдёт дальше + оценка потерь».
**AC:**
- `GET /risks/{id}/scenario` → `{explanation, what_happens_next, estimated_loss, recommended_actions}`.
- Использует TASK-2.3 для цифр, Claude — для нарратива.

# EPIC 3 — Детекция кризиса и триггеры (P1)

### TASK-3.1 — Движок триггеров
**Что:** автоматический перевод риска/инцидента в кризис.
**Правила (из документа):** `Risk Score > 70` ИЛИ резкий рост за 24–48ч; `Score > 90` = Crisis Mode. Сигналы: volume spike, sentiment drop, velocity, source quality, internal signals.
**Где:** фоновый воркер (APScheduler/Celery) + `services/trigger.py`.
**AC:**
- При срабатывании создаётся запись в `crises` с уровнем L1–L4.
- Шлётся alert (см. EPIC 4).
- Тест: подать сигнал со score 95 → создаётся кризис в режиме Crisis Mode.

### TASK-3.2 — Ранние сигналы (Этап 0)
**Что:** фоновый мониторинг индикаторов с порогами.
**Индикаторы:** LTIFR >15%/квартал, овертаймы >20%/3мес, жалобы в соцсетях >5/сутки, падение проходки -10%, текучесть ИТР >25%/полугодие.
**AC:**
- Конфигурируемые пороги в таблице `early_signal_rules`.
- При превышении — уведомление Risk Owner + запись в `risks`.

# EPIC 4 — Crisis Response Center / Оркестратор (P1, ядро правого края)

### TASK-4.1 — Конечный автомат кризиса (фазы 0–5)
**Что:** реализовать жизненный цикл из плейбука: Detection → Activation → Alignment → Execution → Control → Post-Crisis.
**Таблица:** `crisis_phases (crisis_id, phase, started_at, completed_at, artifacts jsonb)`.
**AC:**
- `POST /crises/{id}/advance` двигает фазу с валидацией переходов.
- Каждая фаза фиксирует тайминг (для метрик Time-To-Contain / Time-To-Stabilize).

### TASK-4.2 — Оркестратор-агент
**Что:** сервис, который при кризисе классифицирует, приоритизирует и делегирует.
**Промпт:** системный промпт оркестратора из документа (юрисдикция РК, M-01…M-12, формула приоритета `(Вероятность × Ущерб) / Время_реагирования`).
**AC:**
- `POST /crises/{id}/orchestrate` → JSON-план + человекочитаемое резюме.
- Учитывает матрицу HITL (см. TASK-4.5).

### TASK-4.3 — Координация задач кризисного штаба
**Что:** генерация и трекинг action plan (таблица «Действие/Ответственный/Срок/KPI»).
**Таблица:** `crisis_tasks (id, crisis_id, action, owner_role, deadline, kpi, status)`.
**AC:**
- `POST /crises/{id}/tasks` (авто-генерация плана), `PATCH /crisis_tasks/{id}` (статус).
- Напоминания по дедлайнам (фоновый воркер) + отметки выполнения.

### TASK-4.4 — Организация встречи + почасовая отчётность
**Что:** создание онлайн-встречи ТОПов и авто-отчёт каждый час.
**AC:**
- Интеграция-заглушка для Google Meet/Zoom (генерация ссылки) + рассылка приглашений по email.
- Cron: каждый час, пока кризис открыт, формирует и шлёт статус-отчёт (состояние задач, изменение Risk Score, тональность).

### TASK-4.5 — Матрица HITL
**Что:** какие действия AI делает сам, какие требуют человека.
**Таблица:** `hitl_rules (action, autonomous bool, required_role)`.
**Данные:** из таблицы HITL в документе (остановка участка — авто; релиз, остановка рудника, компенсация семье — HITL).
**AC:**
- Любое действие агента проверяется против `hitl_rules`; при `autonomous=false` создаётся запрос на подтверждение, действие блокируется до апрува.

# EPIC 5 — AI Communication Assistant (P1)

### TASK-5.1 — Генерация коммуникационных материалов
**Что:** пресс-релиз, внутреннее сообщение, письмо регулятору/инвесторам, Q&A для СМИ, посты в соцсети.
**Шаблоны:** взять из документа (внутреннее T+45, внешний релиз T+60–90, соцсети, с учётом РК: соболезнование, неразглашение ФИО, казахский перевод офиц. релизов).
**Где:** `POST /crises/{id}/communications` с параметром `type`.
**AC:**
- Все материалы создаются в статусе `draft`.
- **Обязательное ручное подтверждение перед отправкой** (нельзя отправить без апрува).
- PR-агент соблюдает ограничения промпта (не использует «вина компании»/«халатность» до расследования; всегда вставляет соболезнование).

### TASK-5.2 — GR-агент: тайминги уведомлений госорганов (РК)
**Что:** чек-лист и напоминания по уведомлениям.
**Данные:** акимат T+15, МЧС/112 T+15, прокуратура T+30, МИД/ОВИР T+30 (если иностранец), АП РК T+60 (групповой НС).
**AC:**
- При кризисе уровня L3/L4 авто-создаётся список уведомлений с таймерами и ответственными (GR).
- Просрочка подсвечивается.

### TASK-5.3 — Мониторинг реакции после публикации
**Что:** PR-агент каждые 15 мин проверяет публикации, отчёт каждые 30 мин.
**AC:**
- Отчёт: кол-во публикаций, топ-3 источника, тональность %, 2 главных нарратива, рекомендация (релиз: да/нет/отложить).

# EPIC 7 — Постмортем и самообучение (P2)

**Разделы:** хронология, качество срабатывания AI, эффективность коммуникаций, факт vs прогноз ущерба, юрпоследствия, изменения процессов.

## Порядок реализации (рекомендация)

1. **EPIC 0** — баги (разблокировать работу)
2. **EPIC 1, 2** — модель Risk/Incident + таксономия + формулы (фундамент)
3. **EPIC 3, 4, 5** — детекция → оркестратор → коммуникации (ядро ценности)
4. **EPIC 6, 8** — плейбуки/юрбаза + сбор от ТОПов + отчёт
5. **EPIC 7, 9, 10** — постмортем, интеграции, бэклог

## Общие требования (Definition of Done для всех задач)

- Pydantic-схемы на вход/выход, типизация.
- Миграции (Alembic) для каждой новой таблицы.
- Юнит-тесты на бизнес-логику (особенно формулы и триггеры).
- Все действия AI-агентов проходят через проверку HITL.
- Материалы коммуникаций — только через ручной апрув перед отправкой.
- Логирование таймингов кризиса (Time-To-Contain, Time-To-Stabilize) — главные метрики.
