# Промт для Claude Code — Настройка формул под пользователя (UI + бэкенд)

> Вставь в Claude Code как задачу. Бэкенд — **FastAPI**. Это надстройка над движком скоринга (`risk_engine`, формулы Risk Score / Loss). Сначала прочитай существующий код движка и фронта, адаптируй UI под текущий фреймворк фронтенда.

---

## Цель

Дать **обычному пользователю (не разработчику)** менять, как система оценивает риски — через понятные ручки, без формул и математики. Принцип: **человек крутит контролы, формула в коде неизменна, меняются только её параметры в безопасных границах.**

НЕ давать редактировать саму формулу-выражение. Только: пресеты, слайдеры важности, пороги тревоги, приоритет источников. + живой превью эффекта.

---

## Архитектура

```
UI-контролы (пресеты / слайдеры / тумблеры)
      │ пишут простой JSON-конфиг
      ▼
risk_configs (per user/department)
      │ резолвится в эффективные веса/пороги
      ▼
risk_engine (формула неизменна, берёт веса из конфига)
      │
      ▼
/preview  — пересчёт на последних N сигналах → "было → стало"
```

## Бэкенд

### Модель конфига

```python
risk_configs(
  id, company_id, scope[user|department|company], owner_id,
  preset            str,     # "cautious" | "balanced" | "strict" | "custom"
  weights           jsonb,   # {severity, velocity, signal_density}  каждый 0.5–1.5
  trigger_threshold int,     # 60 | 70 | 80
  source_prefs      jsonb,   # [{source_id, enabled, priority}]
  version, updated_by, updated_at
)
```

Resolution: user → department → company default. Эффективный конфиг = первый найденный.

### Пресеты (заранее заданные наборы)

```python
PRESETS = {
  "cautious":   {"weights": {"severity":1.0,"velocity":1.3,"signal_density":1.2}, "trigger_threshold":60},
  "balanced":   {"weights": {"severity":1.0,"velocity":1.0,"signal_density":1.0}, "trigger_threshold":70},
  "strict":     {"weights": {"severity":1.2,"velocity":0.8,"signal_density":1.0}, "trigger_threshold":80},
}
```

### Маппинг слайдера → вес (границы зашиты, человек не сломает)

Слайдер у пользователя — позиция 0..100 («не очень» … «очень важно»). Конвертация:

```python
def slider_to_weight(pos: int) -> float:        # pos 0..100
    return round(0.5 + (pos / 100) * 1.0, 2)    # → 0.5..1.5

def weight_to_slider(w: float) -> int:
    return round((w - 0.5) / 1.0 * 100)
```

Любое значение клампится в 0.5–1.5 на бэке — даже если фронт пришлёт мусор.

### Эндпоинты

```
GET  /config                      — текущий эффективный конфиг (+ позиции слайдеров для UI)
PUT  /config                      — сохранить (валидация границ, clamp, версия++)
POST /config/preset/{name}        — применить пресет одним кликом
POST /config/reset                — сбросить к стандарту компании
POST /preview                     — вход: черновик конфига; выход: эффект на реальных данных
GET  /sources                     — список источников для тумблеров
```

### Контракт /preview (ключевая фича)

```jsonc
// REQUEST
{ "weights": {...}, "trigger_threshold": 65, "source_prefs": [...] }

// RESPONSE — пересчёт на последних N сигналах (НЕ сохраняя конфиг)
{
  "sample_size": 120,
  "examples": [
    {"signal": "недовольство зарплатами", "score_before": 61, "score_after": 68},
    {"signal": "негатив в СМИ",            "score_before": 44, "score_after": 47}
  ],
  "alerts_before": 3,
  "alerts_after": 5
}
```

Превью пересчитывает score «на лету» с черновыми весами, ничего не записывает в БД.

## Фронтенд (UI-контролы)

Адаптируй под текущий фреймворк. Поведение и тексты — человеческим языком, без слов «вес», «коэффициент», «Velocity».

### 1. Пресеты — три карточки/кнопки

```
🟢 Осторожный          🟡 Сбалансированный (выбран)      🔴 Только серьёзное
Ловим раньше,          Золотая середина                 Тревога реже,
больше тревог                                            только крупное
```
Клик → `POST /config/preset/{name}` → UI обновляется, превью пересчитывается.

### 2. Слайдеры важности (видны при «Настроить вручную»)

```
Что для вас важнее при оценке риска?

Насколько серьёзно           [—————●———]
Как быстро разрастается      [———●—————]
Сколько подтверждений        [——————●——]

Когда поднимать тревогу?
   ○ Рано    ● Средне    ○ Поздно        (60 / 70 / 80 — скрыто от юзера)
```
- Подписи слева/справа: «не очень» … «очень важно».
- Движение слайдера → debounce 300мс → `POST /preview` → показать «было → стало».

### 3. Источники — тумблеры + приоритет

```
Какие источники важнее для вас?
  ⭐ Telegram     [вкл]
     Соцсети      [вкл]
     СМИ          [вкл]
     Форумы       [выкл]
```
Звезда = приоритет, тумблер = enabled. Drag для порядка (опц.).

### 4. Живой превью — всегда на экране

Панель сбоку/снизу, обновляется при любом изменении:
```
Превью на ваших данных (120 сигналов):
  • «недовольство зарплатами»  61 → 68
  • В тревоге сейчас: 3 → станет 5
```

### 5. Кнопки

```
[ Сохранить ]   [ Сбросить к стандарту ]
```
Сохранить → `PUT /config`. Сброс → `POST /config/reset`.

## Безопасность (невидима пользователю)

- Все веса клампятся 0.5–1.5, порог ∈ {60,70,80} — на бэке. Сломать нельзя.
- Простые изменения применяются **сразу, без апрувов**.
- Версионирование + `updated_by`/`updated_at`; в записях риска — `config_version`.
- История **не пересчитывается** задним числом — новый конфиг с момента сохранения.
- Кнопка сброса всегда доступна.

---

## Acceptance Criteria

1. Юзер применяет пресет одним кликом — конфиг и превью меняются.
2. Слайдер двигает вес только в 0.5–1.5; значения вне диапазона клампятся на бэке (тест с мусором на входе).
3. `/preview` возвращает «было → стало» на реальных последних сигналах и **ничего не пишет** в БД (тест: конфиг в БД не изменился).
4. Resolution user→department→company работает; в записи риска сохраняется `config_version`.
5. «Сбросить к стандарту» возвращает к дефолту компании.
6. UI не показывает слова «вес/коэффициент/Velocity» — только человеческие подписи.
7. История скоров не пересчитывается при смене конфига.
8. Alembic-миграции применяются чисто, есть юнит-тесты на `slider_to_weight`/clamp.

## Чего НЕ делать

- НЕ давать редактировать формулу-выражение (только параметры).
- НЕ требовать апрувов на простые изменения слайдеров/пресетов.
- НЕ хардкодить границы в нескольких местах — одна точка истины (settings).
- НЕ пересчитывать историю при смене конфига.

## Порядок реализации

1. Модель `risk_configs` + пресеты + резолвер + миграции.
2. `slider_to_weight` / clamp + юнит-тесты.
3. Эндпоинты `/config`, `/config/preset`, `/config/reset`, `/preview`, `/sources`.
4. UI: пресеты → слайдеры → тумблеры источников → панель превью → кнопки.
5. Связать движение контролов с debounce-превью.
